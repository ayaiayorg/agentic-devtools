# Feature Specification: Standardize Copilot Review PR Response Process

**Feature Branch**: `speckit/1432/phase-1-specify`
**Created**: 2026-05-15
**Status**: Draft
**Source Issue**: #1432 (<https://github.com/ayaiayorg/agentic-devtools/issues/1432>)

## Problem Statement

Currently, the process for responding to Copilot PR reviews uses custom methods for starting
Copilot CLI sessions, and logic for triggering/finalizing the loop is scattered across workflow
YAMLs and Python modules. Suppressed Copilot PR comments require manual intervention and are
easy to miss. The system needs a fully automated, platform-agnostic PR loop using GitHub Actions
(no agent) where non-trivial logic resides in the agentic-devtools Python codebase.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Automated AI Session Trigger (Priority: P1)

As a repository maintainer, I want the system to automatically post a PAT-authenticated PR
comment tagging @copilot when both the Copilot review and PR checks have completed, so that
the AI agent session is triggered without manual intervention.

**Why this priority**: This is the entry point for the entire automated loop — nothing else
can proceed without a reliable trigger mechanism.

**Independent Test**: Can be tested by simulating a completed Copilot review + completed PR
checks and verifying that a correctly formatted @copilot comment is posted to the PR.

**Acceptance Scenarios**:

1. **Given** a Copilot review has completed AND all PR checks have completed, **When** the
   workflow runs, **Then** a PAT-authenticated comment beginning with @copilot is posted to
   the PR using the appropriate template.
2. **Given** only the Copilot review has completed but PR checks are still pending, **When**
   the workflow evaluates, **Then** no comment is posted until checks also complete.
3. **Given** suppressed Copilot review comments exist, **When** the trigger fires, **Then**
   the comment uses the `pr_review_process.md` template and includes the suppressed comments.
4. **Given** no suppressed comments exist, **When** the trigger fires, **Then** the comment
   uses the `ci_review_process.md` template with links to any failing checks and logs.
5. **Given** the trigger comment has been posted and the system is polling for the
   workflow-posted result comment (containing the agent's output), **When** the polling
   timeout expires (15 minutes elapsed without detecting the result comment), **Then** the
   system posts a failure PR comment using the
   workflow's `GITHUB_TOKEN` (author: `github-actions[bot]`) that includes the polling
   duration, the review ID that triggered the session, and a link to the workflow run for
   debugging, and the workflow step exits with a non-zero exit code.

### User Story 2 - Automatic Thread Resolution (Priority: P1)

As a repository maintainer, I want the system to automatically reply to every Copilot review
comment and resolve those threads after the AI agent session completes, so that resolved
feedback is cleaned up without manual work.

**Why this priority**: Thread resolution is critical for maintaining a clean PR state and
enabling re-review cycles.

**Independent Test**: Can be tested by verifying that after the agent result comment appears,
all Copilot review threads receive a reply linking to the result and are resolved.

**Acceptance Scenarios**:

1. **Given** the AI agent session has completed and the workflow has posted the result
   comment (containing the agent's output) via `GITHUB_TOKEN`, **When** the resolution
   step runs, **Then** every comment from the Copilot review receives a reply linking to
   the result comment.
2. **Given** replies have been posted, **When** the resolution step completes, **Then** all
   corresponding review threads are resolved via the GitHub GraphQL API.
3. **Given** a thread resolution fails, **When** the system retries, **Then** it retries up
   to 3 times before reporting the failure.

### User Story 3 - Commit Squash with Generated Message (Priority: P1)

As a repository maintainer, I want PR commits to be squashed into a single commit with a
message generated by calling the Copilot SDK within the GitHub Actions workflow (following
`COMMIT_CONVENTION.md`), so that the force-push from the human PAT re-triggers automatic
Copilot review on a clean single-commit state.

**Why this priority**: Copilot cloud agents cannot force-push. The squash and force-push
must happen programmatically within a GitHub Actions workflow using the same human PAT
that created the PR. Automatic Copilot reviews are configured on the repository and are
triggered by commits from human accounts — the force-push from the human PAT is what
re-triggers the review.

**Independent Test**: Can be tested by verifying that after the agent adds commits, the
system squashes all PR commits into one and the commit message follows the conventions in
`COMMIT_CONVENTION.md`.

**Acceptance Scenarios**:

1. **Given** the AI agent session has added one or more commits to the PR, **When** the
   squash step runs, **Then** all PR commits are squashed into a single commit.
2. **Given** commits are being squashed, **When** the commit message is generated, **Then**
   the system calls the Copilot SDK from within the GitHub Actions workflow, providing it
   with the PR change summary and `COMMIT_CONVENTION.md` conventions, to produce the
   message. If the Copilot SDK is unavailable or times out, a fallback message is
   generated locally from the PR title and commit history following
   `COMMIT_CONVENTION.md` format.
3. **Given** the squash is complete, **When** the system runs
   `git push --force-with-lease` using the human PAT, **Then** the push triggers a fresh
   automatic Copilot review (because the repository has automatic Copilot reviews
   configured and the push comes from a human account).
4. **Given** the squash is complete and the system is about to force-push, **When** the
   PR head SHA has changed since the squash began (e.g., a concurrent push from another
   source), **Then** the system MUST fail gracefully with a conflict error indicating the
   head SHA mismatch rather than overwriting the newer commit.

### User Story 4 - Template-Driven Comment Formatting (Priority: P2)

As a repository maintainer, I want trigger comments to follow project templates with

address all issues.

**Why this priority**: Template consistency ensures the AI agent receives properly
structured instructions every time.

**Independent Test**: Can be tested by comparing generated comments against the expected
template format and verifying all required sections and links are present.

**Acceptance Scenarios**:

1. **Given** PR checks have failed, **When** the trigger comment is generated, **Then** it
   includes direct links to failing check runs and their logs.
2. **Given** the `pr_review_process.md` template is used, **When** suppressed comments
   exist, **Then** all suppressed comments are included in the comment body.
3. **Given** a comment is generated, **When** it is posted, **Then** the @copilot tag
   appears at the very beginning of the comment (not embedded within quoted text).

### User Story 6 - Deduplication of Trigger Comments (Priority: P2)

As a repository maintainer, I want the system to detect and prevent duplicate trigger
comments, so that the AI agent is not invoked multiple times for the same review cycle.

**Why this priority**: Deduplication prevents wasted compute and conflicting agent sessions.

**Independent Test**: Can be tested by simulating the trigger condition firing twice and
verifying only one comment is posted.

**Acceptance Scenarios**:

1. **Given** a trigger comment has already been posted for the current review cycle, **When**
   the workflow fires again, **Then** no duplicate comment is posted.
2. **Given** a new Copilot review is submitted (new review cycle), **When** the workflow
   fires, **Then** a new trigger comment IS posted for the new cycle.

### Edge Cases

- What happens when the Copilot review completes before PR checks, then checks fail later
  and are re-run? The system must wait for the final check state before triggering.
- What happens when the AI agent session fails to produce a result comment? The system must
  time out after 15 minutes and report the failure via a PR comment rather than waiting
  indefinitely.
- What happens when suppressed comments span multiple review submissions? Only comments from
  the current review cycle (identified by the Copilot review ID) should be included.
- What happens when the PAT lacks sufficient permissions? The system must fail gracefully
  with a clear error message indicating the missing permission.
- What happens when a squash force-push races with a new commit from another source? The
  system must verify the head SHA before force-pushing and fail gracefully with a conflict
  error if it has changed.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST post a PAT-authenticated PR comment beginning with @copilot
  when both Copilot review and PR checks have completed.
- **FR-002**: The system MUST NOT post a trigger comment if either Copilot review or PR
  checks are still pending.
- **FR-003**: The trigger comment MUST use the `pr_review_process.md` template when
  suppressed Copilot review comments exist.
- **FR-004**: The trigger comment MUST use the `ci_review_process.md` template when no
  suppressed comments exist.
- **FR-005**: The trigger comment MUST include direct links to any failing PR checks and
  their logs.
- **FR-006**: The @copilot tag MUST appear at the very beginning of the comment body (not
  embedded within quoted text or other content).
- **FR-007**: After the AI agent session completes, the system MUST reply to every comment
  from the Copilot review with a link to the agent's result comment.
- **FR-008**: After replies are posted, the system MUST resolve all corresponding review
  threads via the GitHub GraphQL API.
- **FR-009**: After thread resolution, the system MUST squash all PR commits into a single
  commit.
- **FR-010**: The squashed commit message MUST be generated by calling the Copilot SDK
  from within the GitHub Actions workflow, providing it with the PR change summary
  (changed file paths and selected hunks) and the `COMMIT_CONVENTION.md` conventions.
  If the Copilot SDK is unavailable or times out after 5 minutes, a fallback message
  MUST be generated locally from the PR title and commit history following
  `COMMIT_CONVENTION.md` format.
- **FR-011**: After squashing, the system MUST run `git push --force-with-lease` using
  the same human PAT that was used to create the PR. This force-push from a human
  account automatically re-triggers Copilot review (because automatic Copilot reviews
  are configured on the repository and require a commit from a human account to trigger).
- **FR-012**: The system MUST detect and prevent duplicate trigger comments for the same
  review cycle, using the Copilot review ID as the cycle identifier and a hidden HTML
  comment marker (`<!-- copilot-trigger:REVIEW_ID -->`) for detection. The marker MUST be
  appended after the initial `@copilot` prefix line (not before it) to preserve FR-006
  compliance.
- **FR-013**: All non-trivial logic MUST reside in the agentic-devtools Python codebase,
  not in workflow YAML.
- **FR-014**: The system MUST detect the AI agent's result comment by polling PR comments
  after the trigger, filtering primarily by the sentinel marker
  (`<!-- copilot-agent-result -->`) in the comment body, with the `github-actions[bot]`
  author login as a secondary confirmation. The result comment MUST be posted by the
  workflow step (not the agent directly) using the workflow's `GITHUB_TOKEN` (not the PAT)
  to ensure the author is deterministically `github-actions[bot]`. Maximum polling timeout
  is 15 minutes at 30-second intervals.
- **FR-015**: The system MUST support both the suppressed-comments template and the
  CI-only template selection automatically based on review state.
- **FR-016**: When the FR-014 polling timeout expires (15 minutes elapsed without
  detecting the agent's result comment), the system MUST post a failure PR comment
  using the workflow's `GITHUB_TOKEN` (author: `github-actions[bot]`) that includes:
  (a) the polling duration, (b) the review ID that triggered the session, and
  (c) a link to the workflow run for debugging. The workflow step MUST then exit
  with a non-zero exit code to surface the failure in GitHub Actions.
- **FR-017**: Before executing `git push --force-with-lease`, the system MUST verify
  that the current PR head SHA matches the SHA recorded at the start of the squash
  operation. If the SHA has changed (indicating a concurrent push from another source),
  the system MUST abort the force-push and fail with a clear conflict error message
  including both the expected and actual SHAs.

### Non-Functional Requirements

- **NFR-001**: The end-to-end loop (from trigger to re-triggered Copilot review) MUST complete
  within 10 minutes for a typical PR, excluding: (a) external API latency,
  (b) agent execution time, and (c) the FR-014 result-comment polling window (up to
  15 minutes). The 10-minute budget measures only the system's own processing steps:
  trigger detection, comment posting, thread resolution, squash operation, and
  force-push (which automatically re-triggers Copilot review per FR-011).
- **NFR-002**: The system MUST retry failed GitHub API calls up to 3 times with
  exponential backoff (base delay 2 seconds, multiplier 2×, max delay 16 seconds).
- **NFR-003**: All new code MUST have unit tests following the 1:1:1 test structure
  policy with 100% coverage.
- **NFR-004**: The system MUST be idempotent — re-running the workflow for the same state
  produces no duplicate side effects.
- **NFR-005**: The system MUST log structured audit events for each major step (trigger,
  reply, resolve, squash, force-push) for observability.
- **NFR-006**: Workflow YAML MUST contain only orchestration (job definitions, step
  sequencing, secret injection) with no business logic.
- **NFR-007**: The system MUST produce clear, actionable error messages when a step fails
  (including the specific API error and suggested remediation).

### Key Entities

- **Review Cycle**: A single Copilot review submission and the subsequent automated
  response loop, uniquely identified by the Copilot review ID (numeric, from GitHub's
  review API). A new review cycle begins each time Copilot submits a fresh review (new
  review ID), typically after a force-push from a human PAT that automatically
  re-triggers Copilot review.
- **Trigger Comment**: The PAT-authenticated PR comment that invokes the AI agent session.
  Contains a hidden marker (`<!-- copilot-trigger:REVIEW_ID -->`) appended after the
  initial `@copilot` prefix line for deduplication (preserving FR-006 compliance).
- **Result Comment**: The summary comment posted by the GitHub Actions workflow step
  (not by the AI agent directly) after the agent session completes. The workflow extracts
  the agent's output and posts it via the workflow's `GITHUB_TOKEN` (not the PAT),
  ensuring the author is deterministically `github-actions[bot]`. Identified primarily by
  the sentinel marker (`<!-- copilot-agent-result -->`) in the comment body, with author
  login as secondary confirmation.
- **Review Thread**: A GitHub PR review discussion thread associated with a specific
  comment.
- **Template**: A markdown file stored in `agentic_devtools/prompts/ci/` (the existing
  CI template subdirectory) defining the trigger comment format. Specifically:
  `agentic_devtools/prompts/ci/pr_review_process.md` and
  `agentic_devtools/prompts/ci/ci_review_process.md`. These template files MUST be
  created as part of this feature's implementation. Templates are loaded at runtime via
  the existing `agentic_devtools.prompts.loader` module (which resolves from the package
  data directory, including subdirectories) and support variable substitution for dynamic
  content (check links, suppressed comments, PR context).

   The result comment is posted by the workflow step (not the agent directly) via the
   workflow's `GITHUB_TOKEN` (not the PAT) to ensure the author is deterministically
   `github-actions[bot]`.
2. **Template location**: Templates will be created in `agentic_devtools/prompts/ci/`

## Assumptions

- GitHub Actions has access to a PAT with sufficient permissions (write access to PRs,
  issues, and actions). The PAT is the same human account PAT used to create the PR.
  It is used for the trigger comment (to invoke @copilot) and for
  `git push --force-with-lease` after squashing (to re-trigger automatic Copilot review).
  The workflow's `GITHUB_TOKEN` is used for the result comment (to ensure deterministic
  `github-actions[bot]` authorship).
- The Copilot SDK is available and can be called from within GitHub Actions workflows
  for commit message generation.
- The Copilot review bot (`copilot-pull-request-reviewer[bot]`) and the workflow bot
  (`github-actions[bot]`, used to post the result comment via `GITHUB_TOKEN`) are
  distinct identities that can be differentiated by their login names and sentinel
  markers.
- The `pr_review_process.md` and `ci_review_process.md` templates will be created in
  `agentic_devtools/prompts/ci/` as part of this feature's implementation and follow a
  stable format with variable placeholders.
- Copilot review is automatically re-triggered when a force-push is made from a human
  account PAT, because automatic Copilot reviews are configured on the repository.
- The existing `agdt-gh-resolve-review-threads` and `agdt-gh-reply-to-review-comments`
  commands are functional and their Python implementations can be called directly from
  new orchestration code.
- The existing `agdt-gh-request-copilot-review` command is available as a fallback
  mechanism if the automatic Copilot review re-trigger (via human-PAT force-push per
  FR-011) does not fire within a reasonable window. The primary flow does not call this
  command explicitly — it relies on the force-push auto-trigger.

## Dependencies

- GitHub Actions workflow infrastructure with PAT secret configuration.
- GitHub REST API and GraphQL API for PR operations.
- Copilot SDK for commit message generation within the GitHub Actions workflow (with local
  fallback if the SDK is unavailable or times out).
- Existing `agdt-gh-*` commands for thread resolution and review replies (called as
  Python functions, not subprocesses). The `agdt-gh-request-copilot-review` command is
  available as a fallback if the force-push auto-trigger does not fire.
- Package-bundled templates in `agentic_devtools/prompts/ci/` for comment formatting.
- Existing `agentic_devtools.prompts.loader` module for template loading and variable
  substitution.

## Out of Scope

- Azure DevOps platform adapter (future work — this spec covers GitHub only).
- Modifying how the AI agent session itself operates (the agent is treated as a black box).
- Changing existing `agdt-*` CLI command signatures or behavior.
- Handling fork PRs (only same-repo PRs are in scope).
- Building a custom Copilot agent or modifying Copilot's behavior — the Copilot SDK is
  used only for commit message generation within the GitHub Actions workflow.
