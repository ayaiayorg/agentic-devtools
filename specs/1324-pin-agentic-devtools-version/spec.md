# Feature Specification: Pin agentic-devtools Version in project.json and Guard agdt-setup Against Older Versions

**Feature Branch**: `speckit/1324/phase-1-specify`  
**Created**: 2026-05-04  
**Status**: Draft  
**Input**: User description: "Pin agentic-devtools version in project.json and guard agdt-setup against older versions"  
**Source Issue**: #1324 (<https://github.com/ayaiayorg/agentic-devtools/issues/1324>)

## Problem Statement

When multiple team members run `agdt-setup` at different times, a user with an older version of `agentic-devtools` can inadvertently downgrade repo-managed files (setup scripts, configs, prompts,
agent/prompt skills) that were generated by a newer version. There is currently no mechanism to detect this version mismatch or prevent regression.

The `agdt-setup` command already writes to `.agdt/config/project.json` (for Jira project keys, VPN config, etc.) and uses `__version__` for PR branch naming, but the version is not persisted in the
project config or checked on subsequent runs.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Version Pinning on Successful Setup (Priority: P1)

As a developer running `agdt-setup` for the first time or with a newer version, I want the current `agentic-devtools` version to be recorded in `.agdt/config/project.json` so that the team has a
shared record of the minimum required version.

**Why this priority**: This is the foundational capability — without recording the version, no subsequent guard logic can function. Every other story depends on this.

**Independent Test**: Run `agdt-setup` against a repo with no `agdt_version` in `project.json`. After completion, verify that `project.json` contains the correct `agdt_version` value matching the
running package version. Run again with the same version and verify the value is unchanged. Run with a newer version and verify the value is updated.

**Acceptance Scenarios**:

1. **Given** a repo with no `agdt_version` in `project.json`, **When** `agdt-setup` completes successfully, **Then** `project.json` contains `"agdt_version": "<current_version>"` and all other existing
   config keys are preserved.
2. **Given** a repo where `project.json` has `"agdt_version": "0.2.69"` and the running version is `0.2.70`, **When** `agdt-setup` completes successfully, **Then** `agdt_version` is updated to
   `"0.2.70"`.
3. **Given** a repo where `project.json` has `"agdt_version": "0.2.69"` and the running version is also `0.2.69`, **When** `agdt-setup` completes successfully, **Then** `agdt_version` remains `"0.2.69"`
   (no-op update).

### User Story 2 — Block Downgrade on Older Version (Priority: P1)

As a developer who accidentally has an older version of `agentic-devtools` installed, I want `agdt-setup` to refuse to modify repo files and clearly tell me how to upgrade, so that I do not
inadvertently regress work done by teammates with a newer version.

**Why this priority**: This is the core safety guard — the primary motivation of the feature. Without this, the version pin from Story 1 is unused metadata.

**Independent Test**: Set `project.json` to `"agdt_version": "0.2.69"`, then run `agdt-setup` from a build with version `0.2.64`. Verify that an error is printed, no repo files are modified, no branch
is created, no PR is opened, and the exit code is non-zero.

**Acceptance Scenarios**:

1. **Given** `project.json` records `"agdt_version": "0.2.69"` and the running version is `0.2.64`, **When** the user runs `agdt-setup`, **Then** an error message is printed to stderr stating the
   version mismatch, recommending `python setup-dev-tools.py` to upgrade, and mentioning `--force-old-version` as an escape hatch. No repo files are written, no branch is created, no PR is opened. The
   process exits with a non-zero exit code.
2. **Given** `project.json` records `"agdt_version": "0.2.69"` and the running version is `0.2.64`, **When** the user runs `agdt-setup`, **Then** the `agdt_version` in `project.json` is NOT modified
   (remains `"0.2.69"`).
3. **Given** `project.json` does not contain `agdt_version` (first-time setup or legacy repo), **When** the user runs `agdt-setup` with any version, **Then** setup proceeds normally (no version guard
   is triggered) and `agdt_version` is written.

### User Story 3 — Force Override for Local-Only Steps (Priority: P2)

As a developer who needs to configure my local environment but cannot upgrade right now, I want a `--force-old-version` flag that allows `agdt-setup` to run local-only configuration steps (cert
prefetch, shell profile, dependency checks) while still skipping all repo file mutations.

**Why this priority**: Provides an escape hatch for real-world scenarios where upgrading is temporarily impossible (e.g., broken CI, version not yet released to PyPI). Lower priority than the hard
block because the default-safe behaviour (Story 2) is more important.

**Independent Test**: With a pinned version newer than the running version, run `agdt-setup --force-old-version`. Verify that local steps run (certs, dependency check, shell profile) but
repo-modifying steps are skipped (no `.agdt/.gitignore` write, no skill injection, no platform config write, no template generation, no branch/PR creation). Verify a warning is logged.

**Acceptance Scenarios**:

1. **Given** `project.json` records `"agdt_version": "0.2.69"` and the running version is `0.2.64`, **When** the user runs `agdt-setup --force-old-version`, **Then** a warning is printed explaining
   that repo files will not be modified, local-only steps execute normally (cert prefetch, managed installs, dependency checks, shell profile persistence), and the command exits with code 0.
2. **Given** `project.json` records `"agdt_version": "0.2.69"` and the running version is `0.2.64`, **When** the user runs `agdt-setup --force-old-version`, **Then** the following repo-modifying steps
   are skipped: `.agdt/.gitignore` creation, skill injection, project config prompts, platform detection/config, workflow template generation, PR branch creation, and PR creation.
3. **Given** `project.json` records `"agdt_version": "0.2.69"` and the running version is `0.2.64`, **When** the user runs `agdt-setup --force-old-version`, **Then** the `agdt_version` in `project.json`
   is NOT modified (remains `"0.2.69"`).
4. **Given** the running version is equal to or newer than `agdt_version`, **When** the user passes `--force-old-version`, **Then** the flag is ignored (no-op) and setup proceeds normally.

### Edge Cases

- What happens when `project.json` contains an `agdt_version` value that is not a valid PEP 440 version string (e.g., `"abc"` or `""`)? The system should treat it as if no version is pinned and
  proceed normally, logging a warning about the malformed value. Validity is defined by whether `packaging.version.Version` can parse the value without raising `InvalidVersion`.
- What happens when `project.json` does not exist at all? The system should proceed normally (first-time setup) and create `project.json` with `agdt_version`.
- What happens when comparing pre-release versions (e.g., `0.2.69.dev1` vs `0.2.69`)? The system should use PEP 440-compliant version comparison (via `packaging.version.Version`) so that
  dev/pre-release versions are correctly ordered.
- What happens when `--force-old-version` is combined with `--skip-pr-workflow`? Both flags should be respected independently — `--force-old-version` suppresses repo-modifying steps regardless of PR
  workflow settings.
- What happens when `--force-old-version` is combined with `--system-only`? Both flags should be respected — the version guard fires first (or is bypassed), then `--system-only` further limits what
  runs.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: During `agdt-setup`, the system MUST write the current `agentic-devtools` version to `.agdt/config/project.json` under the key `agdt_version` upon successful completion of all
  repo-modifying steps. Specifically: any validation or check that could cause a non-zero exit (e.g., missing required dependencies, failed pre-flight validation) MUST execute **before** any
  repo-mutating steps run. This "fail-fast before mutations" constraint ensures that once repo-modifying steps begin, the process will complete successfully and the version pin will be recorded.
  The version write MUST occur immediately after all repo-modifying steps have succeeded — even if optional post-setup checks (e.g., informational diagnostics) run afterward. If a repo-modifying
  step itself fails, the version MUST NOT be written and the process MUST exit non-zero. This does NOT apply when `--force-old-version` is active (see FR-008).
- **FR-002**: The version MUST be written as a string value (e.g., `"0.2.69"`) sourced from `agentic_devtools.__version__`.
- **FR-003**: On subsequent `agdt-setup` runs, the system MUST compare the running version against the `agdt_version` recorded in `project.json` using PEP 440-compliant version comparison.
- **FR-004**: If the running version is strictly older than the recorded `agdt_version` **and `--force-old-version` is NOT specified**, the system MUST print an error to stderr, skip all repo file
  mutations, and exit with a non-zero exit code. When `--force-old-version` IS specified, the system MUST instead print a warning and continue with local-only steps (see FR-007/FR-009).
- **FR-005**: The error message (non-force path) MUST include: (a) the running version, (b) the required version, (c) a recommendation to run `python setup-dev-tools.py`, (d) mention of the
  `--force-old-version` flag.
- **FR-006**: If the running version is equal to or newer than the recorded `agdt_version`, setup MUST proceed normally and update `agdt_version` to the current version.
- **FR-007**: The `--force-old-version` flag MUST allow `agdt-setup` to run local-only steps (cert prefetch, managed installs, dependency checks, shell profile persistence) while skipping all
  repo-modifying steps.
- **FR-008**: When `--force-old-version` is used, the system MUST NOT update `agdt_version` in `project.json`.
- **FR-009**: When `--force-old-version` is used, the system MUST print a warning that repo files will not be modified and that this mode is not recommended.
- **FR-010**: The version guard MUST NOT trigger when `project.json` does not exist or does not contain `agdt_version` (first-time setup scenario).
- **FR-011**: The version guard MUST NOT trigger when `agdt_version` contains a malformed/unparseable value; in this case, a warning should be logged and setup should proceed normally.
- **FR-012**: Writing `agdt_version` MUST preserve all existing keys in `project.json` (use the existing `load_project_config` / `save_project_config` pattern).
- **FR-013**: The implementation MUST update the root `.gitignore` to add negation rules in the correct order: `!.agdt/` (unignore the parent directory), then `!.agdt/config/`, then
  `!.agdt/config/project.json`. These negation rules MUST be placed *after* the existing `.agdt/` ignore rule in the file; Git processes `.gitignore` top-to-bottom and a negation rule only
  takes effect if it appears after the pattern it negates. Additionally, Git requires each ancestor directory to be unignored before child negation rules take effect. Without `!.agdt/` first,
  the subsequent negation rules are silently ignored. This ensures `project.json` is tracked by Git and shared across teammates, despite the existing `.agdt/` ignore rule.

### Non-Functional Requirements

- **NFR-001**: The version check MUST execute before any file-modifying step, adding negligible latency (< 50ms) to the setup flow.
- **NFR-002**: Error and warning messages MUST follow the existing `agdt-setup` output style (using `✓`, `⚠`, emoji-prefixed lines, `print(..., file=sys.stderr)` for errors/warnings).
- **NFR-003**: The `packaging` library MUST be listed as an explicit runtime dependency in `pyproject.toml` and used for version comparison to ensure PEP 440 compliance. If `packaging` is
  unavailable at runtime (e.g., in a broken environment), the system MUST fall back to a best-effort numeric segment comparison that is **non-throwing** and uses the following deterministic rules:
  1. Split each version string on `.` to produce a list of segments.
  2. For each segment, attempt to parse it as an integer. If parsing succeeds, use the integer value.
  3. If a segment cannot be parsed as an integer (contains non-digit characters), apply the following decomposition:
     - First, extract the leading numeric prefix (if any) using a regex such as `^(\d+)(.*)$`. This splits a segment like `70rc1` into numeric part `70` and suffix `rc1`.
     - If a leading numeric prefix exists, expand the segment into **two** comparison elements: the numeric prefix as an integer, followed by a suffix-order value derived from the remaining
       text (see suffix ordering below).
     - If no leading numeric prefix exists (the segment starts with a non-digit character), treat the entire segment as a suffix and expand it into **two** comparison elements: `0` (neutral
       numeric base), followed by the suffix-order value.
     - **Suffix ordering values**: `post` → `+1` (post-release is newer than the base release at this position); `dev`, `alpha`, `a`, `beta`, `b`, `rc`, `c`, or any other non-numeric suffix
       → `-1` (pre-release is older than the base release at this position). Extract the suffix keyword by stripping trailing digits from the remaining text.
     - Example decompositions: `70rc1` → `[70, -1]`; `post0` → `[0, +1]`; `dev1` → `[0, -1]`; `69` → `[69]`.
  4. After decomposition, each version is represented as a flat list of integers. Pad the shorter list with `0` values so both lists have equal length.
  5. Compare the two integer lists lexicographically (element by element, left to right).
  6. Local version metadata (anything after `+` in the version string) MUST be stripped before comparison and ignored entirely.
  7. If any unexpected error occurs during parsing, the fallback MUST default to allowing setup to proceed (fail-open) rather than raising.

  Log a warning indicating that PEP 440 pre-release ordering is not guaranteed under this fallback.
- **NFR-004**: All new logic MUST have 100% test coverage following the 1:1:1 test structure policy.

### Key Entities

- **`project.json`** (``.agdt/config/project.json``): Existing team-shared, repo-committed configuration file. Gains a new `agdt_version` key recording the `agentic-devtools` version used during the
  last successful `agdt-setup` run. Note: The root `.gitignore` currently ignores `.agdt/` entirely. To allow `project.json` to be tracked and shared across teammates, the implementation MUST add
  negation rules to the root `.gitignore` in the correct order (`!.agdt/`, `!.agdt/config/`, `!.agdt/config/project.json` — Git requires ancestor directories to be unignored first) or relocate the
  config to a tracked path. The managed `.agdt/.gitignore` only ignores runtime state (`workflows/`, `runtime-bootstrap.json`, `identity.json`), so once the root negation rules are in place,
  `project.json` will be properly tracked.
- **`agdt_version`**: String value in `project.json`. Represents the minimum `agentic-devtools` version the repo expects. Updated on each successful setup with an equal-or-newer version. Never
  downgraded by `agdt-setup`.
- **`--force-old-version`**: New CLI flag for `agdt-setup`. Bypasses the version guard but restricts the command to local-only (non-repo-mutating) operations.
